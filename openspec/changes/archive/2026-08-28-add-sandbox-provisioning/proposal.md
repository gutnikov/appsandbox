## Why

Платформы zerotomvp пока нет: репозиторий пуст, домен куплен, но входа в продукт не существует. Первый осмысленный срез — превратить посетителя в владельца сэндбокса: лендинг, вход через GitHub, созданный из шаблона репозиторий в его аккаунте и закреплённое за ним имя поддомена.

Этот change сознательно не включает запуск прототипа, но фиксирует то, что дороже всего менять потом: контракт шаблона сэндбокса, путь доставки его образа и правила именования, от которых зависит DNS. Всё перечисленное живёт в репозиториях пользователей, куда мы не сможем внести правки задним числом.

## What Changes

- Заводится второй наш репозиторий `gutnikov/sandbox-template`: Hono + React + Vite + shadcn, `Dockerfile`, `/healthz`, чтение `PORT` из окружения, workflow сборки и публикации образа. Репозиторий публичный, с флагом Template.
- Появляется приложение zerotomvp: лендинг с единственным действием «создать сэндбокс», серверные роуты OAuth, страница результата.
- Вводится GitHub OAuth App (отдельные приложения для dev и prod) со скоупом `public_repo`. Токен пользователя используется в рамках одного запроса и не сохраняется.
- Вводится реестр имён сэндбоксов в Neon: имя резервируется на нашей стороне до обращения к GitHub, потому что имя — это глобальный поддомен, а не запись внутри аккаунта пользователя.
- Имена генерируются автоматически в формате `sandbox-<adjective>-<noun>`; обязательный префикс `sandbox-` структурно исключает захват наших собственных поддоменов (`www`, `api`, `app`).
- Поднимается собственный реестр образов сэндбоксов. Workflow в репозитории пользователя пушит туда образ, аутентифицируясь удостоверением запуска (OIDC), которое платформа обменивает на короткоживущие права ровно на один образ. GHCR для образов сэндбоксов непригоден: пакет личного аккаунта всегда создаётся приватным, видимость от репозитория не наследуется, а API для её смены не существует.
- Настраивается доставка: `Dockerfile` приложения, `config/deploy.yml` для Kamal, образ платформы в GHCR, деплой на VPS, DNS на апекс, wildcard и реестр, TLS. Без публичного URL OAuth callback непроверяем, поэтому деплой входит в скоуп.

## Capabilities

### New Capabilities

- `landing`: публичная страница входа в продукт и страница результата создания сэндбокса.
- `auth/github-oauth`: вход через GitHub, обмен кода на токен, защита от CSRF, правила обращения с токеном и сессионной кукой.
- `sandbox-naming`: генерация, формат и резервирование имени сэндбокса как глобального идентификатора и поддомена.
- `sandbox-provisioning`: создание репозитория пользователя из шаблона и связывание его с зарезервированным именем.
- `sandbox-template`: требования к содержимому шаблона — контракт, по которому платформа позже сможет запустить прототип.
- `sandbox-image-registry`: приём образов сэндбоксов и выдача прав на публикацию по удостоверению запуска GitHub Actions.
- `platform-deployment`: сборка и доставка самой платформы на VPS, домены и TLS.

### Modified Capabilities

Нет: в проекте пока нет ни одной существующей спеки.

## Impact

- Новый код: всё приложение с нуля (Hono, React, TanStack, Vite, shadcn, TypeScript).
- Новый репозиторий: `gutnikov/sandbox-template`.
- Новый сервис на VPS: реестр образов на `registry.zerotomvp.xyz`, доверяющий токенам, которые подписывает платформа.
- Внешние системы: GitHub OAuth Apps (dev + prod), GitHub REST API (`POST /repos/{owner}/{repo}/generate`), OIDC-провайдер GitHub Actions, GHCR (только для образа самой платформы), Neon, DNS зоны `zerotomvp.xyz`, VPS.
- Секреты: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `DATABASE_URL`, `SESSION_SECRET`, ключ подписи токенов реестра — через Kamal secrets.
- Отложено намеренно: запуск контейнеров сэндбоксов, роутинг `*.zerotomvp.xyz` на них, политика хранения образов, список «мои сэндбоксы».
