## Context

Репозиторий платформы пуст, домен `zerotomvp.xyz` куплен, VPS есть. Мотивация — см. `proposal.md`.

Ключевое ограничение, из которого вытекает почти вся конструкция: имя сэндбокса — это поддомен, то есть глобальный ресурс, а прототип — фулстек-приложение, то есть запускать его придётся контейнером. Второе ограничение — поддомены `*.zerotomvp.xyz` будут отдавать код пользователей, что делает основной домен соседом недоверенного кода.

## Goals / Non-Goals

**Goals:**
- Сквозной путь «посетитель → владелец репозитория» работает на живом домене.
- Контракт шаблона зафиксирован так, чтобы хостинг сэндбоксов можно было добавить, не переделывая уже созданные пользовательские репозитории.
- Платформа не становится хранителем чужих учётных данных.

**Non-Goals:**
- Запуск контейнеров сэндбоксов и роутинг `*.zerotomvp.xyz` на них.
- Политика хранения образов и сборка мусора в реестре.
- Аккаунты платформы, список «мои сэндбоксы», удаление сэндбокса.
- Лимиты и защита от злоупотреблений.

## Decisions

### OAuth App, а не GitHub App

Создание репозитория в **личном** аккаунте пользователя надёжно работает через user-токен OAuth App. У GitHub App установка привязана к существующим репозиториям, а создание нового упирается в account-level `Administration: write`, чья работоспособность для user-аккаунта требует проверки. Мы не готовы делать этот риск блокером первого релиза.

Альтернатива (GitHub App) остаётся правильной, когда платформе понадобится **постоянный** доступ к репозиторию — писать в него, читать приватные сэндбоксы, ставить вебхуки. Тогда это отдельный change, и он не ломает уже созданные репозитории.

### Публичные сэндбоксы и скоуп `public_repo`

`public_repo` даёт экран согласия «доступ к публичным репозиториям». Приватные сэндбоксы потребовали бы скоупа `repo` — «полный контроль над приватными репозиториями», включая все существующие репозитории пользователя. На лендинге незнакомого продукта это неприемлемая цена. Публичность прототипа к тому же полезна: ссылкой можно делиться.

Побочная выгода: публичный репозиторий платформа сможет клонировать без каких-либо токенов.

### Токен не хранится — и отсюда способ сборки

Раз токен живёт один запрос, платформа не может позже поставить вебхук на репозиторий пользователя. Развилка была такая:

- **А. Вебхук + сборка у нас.** Вебхук надо создавать сразу после порождения репозитория, пока токен жив. Требует скоупа шире `public_repo` и портит экран согласия.
- **Б. Сборка в Actions пользователя.** В шаблоне лежит workflow: push → сборка образа → публикация в реестр. Ноль дополнительных скоупов, ноль хранимых токенов, сборка идёт на раннерах GitHub (для публичных репозиториев бесплатно), и это та же модель, по которой катится сама платформа: образ в реестр, оттуда запуск.

Выбран **Б**. Плата — workflow виден пользователю и может быть удалён; последствия ограничены его собственным сэндбоксом (см. спеку `sandbox-template`).

### Реестр образов сэндбоксов — свой, а не GHCR

Исходно предполагалось, что workflow пушит образ в GHCR владельца репозитория, а платформа тянет его анонимно. Проверка документации GitHub (задача 1.1) это исключила — см. раздел Risks. Автоматически открыть пакет нельзя ни из workflow, ни вообще через API.

Поэтому образы сэндбоксов складываются в собственный реестр платформы на `registry.zerotomvp.xyz`. Мы контролируем доступ, хранение и удаление, и не зависим от чужой модели видимости пакетов.

Альтернатива, от которой отказались: клонировать публичный репозиторий и собирать образ самим. Это сняло бы и реестр, и workflow, и любую зависимость шаблона от наших endpoint'ов, но перенесло бы сборку произвольного пользовательского кода на наш VPS и лишило бы бесплатных раннеров GitHub.

### Права на публикацию — по удостоверению запуска, без секретов в репозитории

Workflow в чужом репозитории не должен нести наших секретов, а мы не должны хранить чужих. GitHub Actions выдаёт запуску OIDC-токен, в котором зашит репозиторий-источник; этого достаточно, чтобы платформа поверила «этот push действительно идёт из `<owner>/<sandbox-name>`».

Реестр настраивается на делегированную аутентификацию: он не проверяет пароли сам, а отправляет клиента за токеном на endpoint платформы. Туда workflow приходит с OIDC-токеном вместо пароля, платформа его проверяет и выдаёт короткоживущий токен с правом записи ровно в один образ. Отдельного «обменного» endpoint не нужно — realm реестра и есть точка обмена.

Следствие, которое надо принять осознанно: workflow в репозитории пользователя жёстко зависит от доступности нашего реестра. Сделать этот шаг неблокирующим нельзя — он и есть доставка. Поэтому реестр и endpoint выдачи прав входят в этот change: выпустить шаблон с workflow, которому некуда пушить, нельзя, а задним числом workflow в уже созданных репозиториях не исправить.

Приятное следствие: отдельное уведомление платформы о новом образе не нужно. Реестр наш, появление образа мы видим у себя.

### Имя резервируется у нас до обращения к GitHub

Имя — глобальный поддомен, поэтому арбитром уникальности должна быть наша база, а не аккаунт пользователя. Порядок: сгенерировать → вставить в `sandboxes` с уникальным индексом → создать репозиторий → при неудаче удалить резерв. Уникальный индекс, а не «проверить и вставить»: только он корректно разрешает гонку двух одновременных запросов.

Обратный порядок (сначала GitHub, потом запись) допускал бы два сэндбокса с одним поддоменом у разных пользователей — то есть выданный и неисполнимый адрес.

### Обязательный префикс `sandbox-`

Сэндбоксы живут на тех же поддоменах третьего уровня, что и служебные имена платформы. Префикс делает пересечение структурно невозможным: `www`, `api`, `app`, `mail` недостижимы для генератора. Это дешевле и надёжнее списка запрещённых слов, который придётся поддерживать.

### Куки только host-only

Кука с `Domain=.zerotomvp.xyz` была бы доступна коду любого сэндбокса. Поэтому куки платформы ставятся без атрибута `Domain`. Запас прочности «сэндбоксы на отдельном домене» сознательно не берём: с host-only куками и отсутствием доверия к поддоменам текущая схема достаточна.

### Одно приложение: API и SPA вместе

Hono отдаёт и JSON-роуты, и собранный Vite-бандл. Один образ, один деплой-таргет, никаких CORS и никакой отдельной раздачи статики. Разделение фронта и бэка на этом объёме не даёт ничего, кроме второго места, куда надо катить.

Callback OAuth обязан быть серверным роутом — client secret не может попасть в браузер.

### Два OAuth App

У GitHub OAuth App ровно один callback URL, поэтому dev и prod — разные приложения с разными парами секретов. Единственная альтернатива, туннель на локальную машину, делает локальную разработку зависимой от внешнего сервиса.

## Risks / Trade-offs

- **GHCR в аккаунте пользователя непригоден как реестр образов сэндбоксов** (проверено по документации GitHub, задача 1.1):
  - пакет, впервые опубликованный в личном аккаунте, всегда приватный;
  - пакет наследует от связанного репозитория права доступа, но **не видимость**, поэтому публичность репозитория сэндбокса его публичным не делает;
  - REST API смены видимости пакета не существует — только UI.

  Автоматически открыть пакет из workflow нельзя, а требовать от пользователя ручного действия после каждого создания сэндбокса недопустимо. Решение о замене — см. раздел «Кто собирает образ».
- **Workflow пользователя зависит от нашего реестра** → недоступность реестра делает сборки в чужих репозиториях красными. Смягчение: реестр — отдельный контейнер на том же VPS, его падение не связано с выкатом платформы; повторный запуск workflow чинит ситуацию без участия платформы.
- **Хранение образов не ограничено** → каждый push нового коммита добавляет слой в реестр. Политика хранения и сборка мусора отложены в хостинг-change; на объёмах первых сэндбоксов это не проблема, но откладывать бесконечно нельзя.
- **Короткий срок жизни OIDC-токена** → токен запроса действует минуты. Если сборка образа идёт дольше и логин протух, push упадёт. Смягчение: получать токен непосредственно перед push, а не в начале job.
- **Пользователь удаляет workflow сборки** → его сэндбокс перестаёт обновляться. Осознанная плата за вариант Б; влияние ограничено его сэндбоксом.
- **TLS на произвольные поддомены** → сертификат на каждый поддомен по требованию упирается в лимиты Let's Encrypt при массовом создании. Альтернатива — wildcard-сертификат через DNS-01 на всю зону. Решается в хостинг-change; здесь достаточно, чтобы DNS был готов.
- **Утечка сессии через сэндбокс** → куки host-only, никаких доверенных поддоменов.
- **Гонка при выдаче имени** → уникальный индекс в базе плюс ограниченное число повторов генерации.
- **Осиротевшие резервы имён** → освобождение имени в ветке ошибки. Полностью атомарным это не сделать: если процесс упадёт между резервом и созданием репозитория, имя останется занятым. Цена — одно потерянное имя из большого пространства; чистку можно добавить позже.
- **Нет списка сэндбоксов пользователя** → следствие отказа от хранения токена. Реестр хранит `github_login`, поэтому список можно собрать позже без повторной авторизации.

## Migration Plan

Миграции нет: проект создаётся с нуля, обратной совместимости ломать нечего.

Порядок выката: DNS (апекс, wildcard, реестр) → реестр и endpoint выдачи прав → prod OAuth App → первый деплой платформы → шаблонный репозиторий с workflow → проверка сквозного сценария на живом домене. Шаблон выпускается последним: workflow в нём осмыслен только когда реестру есть куда принимать. Откат — предыдущий образ.

Первая схема базы — одна таблица `sandboxes`; накатывается миграцией, а не вручную, чтобы дальнейшие изменения были воспроизводимы.
